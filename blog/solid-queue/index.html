Solid Queue in Rails 8.1: A Practical Guide to Database-Backed Jobs

Solid Queue lets a Rails application run durable background work with the database it already operates. Here is a production-minded path from setup to observability.

By Mauro Ponce · August 19, 2026 · 12 min read

Why Solid Queue?

Rails 8 uses Solid Queue as its production Active Job backend by default. It stores scheduled, ready, running, and failed work in SQL tables, so a small or medium Rails application can run durable jobs without also owning a Redis-backed queue. You still use the familiar Active Job API, which keeps the job code portable if your operational needs later change.

It is a strong fit when the application already runs PostgreSQL, MySQL, or SQLite, job throughput is within what the database can comfortably support, and reducing infrastructure is more valuable than operating a separate queue service. It is not magic: workers are still a separate production process, jobs still need idempotency, and database capacity still needs to be monitored.

Set up a queue database

New Rails 8 applications include the Solid Queue wiring in production. Enabling the same adapter locally gives development behavior that more closely resembles production. A dedicated queue database is the default and is usually the safer boundary: job traffic does not compete as directly with primary application tables, and application code does not accidentally depend on cross-database transactional behavior.

# config/environments/development.rb
config.active_job.queue_adapter = :solid_queue
config.solid_queue.connects_to = { database: { writing: :queue } }
# config/database.yml
development:
  primary:
    <<: *default
    database: storage/development.sqlite3
  queue:
    <<: *default
    database: storage/development_queue.sqlite3
    migrations_paths: db/queue_migrate

For PostgreSQL or MySQL, use the same pattern with a separate queue database and credentials appropriate to that environment. Prepare its tables and start the supervisor:

bin/rails db:prepare
bin/jobs start

The generated queue schema contains the tables Solid Queue uses to move work through its lifecycle. Your deploy should run database preparation before workers begin accepting jobs.

Write jobs with Active Job

The application code remains ordinary Active Job. Pass records or simple serializable arguments, make the work safe to retry, and choose an explicit queue for work that deserves a separate service level.

# app/jobs/generate_report_job.rb
class GenerateReportJob < ApplicationJob
  queue_as :reports
  queue_with_priority 25

  retry_on Faraday::TimeoutError, wait: :polynomially_longer, attempts: 5
  discard_on ActiveJob::DeserializationError

  limits_concurrency to: 1,
                     key: ->(report) { report.account_id },
                     duration: 10.minutes

  def perform(report)
    report.generate!
  end
end
# Run now, later, or at a specific time.
GenerateReportJob.perform_later(report)
GenerateReportJob.set(wait: 5.minutes).perform_later(report)
GenerateReportJob.set(wait_until: tomorrow.noon).perform_later(report)

Concurrency controls are especially useful for work that targets a shared account, vendor API, or resource. The limit does not replace idempotency: a worker can die after an external side effect but before Rails records completion. Use durable identifiers, provider idempotency keys where available, and state transitions that can be safely repeated.

Configure workers, queues, and priorities

config/queue.yml describes the processes that dispatch future work and the workers that execute ready work. Queue order comes before numeric job priority, so reserve earlier queues for work that must not wait behind bulk jobs.

# config/queue.yml
production:
  dispatchers:
    - polling_interval: 1
      batch_size: 500
  workers:
    - queues: [critical, default, reports, low]
      threads: 3
      processes: <%= ENV.fetch("JOB_CONCURRENCY", 1) %>
      polling_interval: 0.1

Start conservatively. Threads increase database connections and concurrent external calls; processes increase memory and CPU use. Measure job latency, database load, and the throughput of the downstream services before increasing either value. Prefer explicit queue names over broad wildcard matching in a busy SQL-backed system.

Schedule recurring work

Recurring tasks live in config/recurring.yml. Use them for cleanup, periodic synchronization, or scheduled reports, and keep the job implementation idempotent in case a deploy or operator action causes a run to be repeated.

# config/recurring.yml
production:
  prune_expired_reports:
    class: PruneExpiredReportsJob
    schedule: every day at 3am

  refresh_vendor_catalog:
    class: RefreshVendorCatalogJob
    schedule: every hour

The scheduler enqueues these jobs; workers still need to be running to perform them. Treat the schedule as application configuration and review it in the same pull request as the job it invokes.

Understand transaction boundaries

A separate queue database means the job insert cannot be part of the primary database transaction. In most applications, explicitly deferring enqueueing until the surrounding transaction commits is a clearer and more portable rule:

# app/jobs/application_job.rb
class ApplicationJob < ActiveJob::Base
  self.enqueue_after_transaction_commit = true
end

That prevents a job from observing a record that was rolled back. If you intentionally use the same ACID database for application and queue data, Solid Queue can offer stronger transactional coupling, but that is a sharp tool: moving the queue to a separate database or adapter later changes those assumptions. Design jobs so the application remains correct without relying on that coupling.

Run it in production

A web server accepting requests is not enough. Run bin/jobs start as a separately supervised process or through the supported Puma integration, give it the same release, environment variables, and database access as the web process, and ensure it receives graceful shutdown signals during deploys.

  • Run queue database preparation before starting workers for a new release.
  • Use persistent storage if the queue database is SQLite; ephemeral disks turn durable jobs into disposable jobs.
  • Set connection-pool sizes with web threads, worker threads, and worker processes in mind.
  • Record structured job failures and alert on growing ready, scheduled, or failed queues.
  • Use a job dashboard such as Mission Control Jobs when operators need to inspect, retry, or discard work.
A useful operating rule: treat a background job as an at-least-once message. Make side effects idempotent, use retries deliberately, and monitor queue age rather than assuming a successful enqueue means successful completion.

Common mistakes to avoid

  • Testing only with the async adapter. Enable Solid Queue locally or in a staging environment so migrations, worker startup, and queue-specific failures are exercised before production.
  • Letting one queue starve another. Earlier queue names are exhausted before later queues are considered. Keep critical and bulk work separate and inspect their latency independently.
  • Passing fragile arguments. Prefer GlobalID-backed records or simple values; handle deleted records with discard_on where that is the correct business outcome.
  • Scaling workers before measuring the database. A database-backed queue trades an extra service for database work, not for no work.
  • Ignoring shutdown behavior. Deploy tooling should allow workers to finish or safely abandon in-flight work according to the job’s retry and idempotency design.
